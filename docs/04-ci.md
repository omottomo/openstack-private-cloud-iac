# 4. 형상관리와 CI — 사설 GitLab CE + 검사 파이프라인

> IaC 파일을 **사설 형상관리 구조**로 관리한다. 노트북에 GitLab CE를 올려 "외부 SaaS 없이
> 사설 Git 서버 + 사설 러너 + push 트리거 자동 검사"를 1대 규모로 재현했다.
>
> 저장소 루트의 [`.gitlab-ci.yml`](../.gitlab-ci.yml)이 그때 실제로 돌린 파이프라인이다.
> **GitHub에서는 실행되지 않는다** — 로컬 GitLab CE 기준으로 작성된 파일을 결과물로 남겨 둔 것이다.

---

## 4-1. 구성

```
Mac 노트북                                  DevStack 호스트
├── gitlab-ce 컨테이너                      └── /opt/stack/terraform/   ← git 작업 복사본
│     :8929  사설 Git 서버 + CI 스케줄러          ├── *.tf, templates/   (형상관리 대상)
│     프로젝트: openstack-iac                    ├── terraform.tfstate  (git 제외)
└── gitlab-runner 컨테이너                       └── terraform.tfvars   (git 제외)
      docker executor — job마다 컨테이너 생성

흐름: 호스트에서 .tf 수정 → 브랜치 push → 파이프라인이 fmt/tflint/validate/tfsec 실행
      → MR 리뷰 → main 머지 → 호스트에서 사람이 `terraform apply`
```

**핵심 설계 판단 1 — 형상관리 대상은 "실제로 apply되는 파일 그 자체"여야 한다.**
처음에는 문서(런북)에서 코드를 복원해 노트북 저장소에 뒀는데, 그 사본이 실환경과 달라져
있었다 ([troubleshooting #11](troubleshooting.md) — openstack-exporter 설정이 통째로 빠져
있었다). 그래서 **`/opt/stack/terraform` 자체를 git 작업 복사본으로 만들고** 노트북 쪽 사본은
지웠다. 사본이 하나뿐이면 "어느 것이 진짜인가" 문제가 생길 수 없다.

**핵심 설계 판단 2 — apply는 파이프라인에 넣지 않았다.** state와 자격증명이 DevStack
호스트에만 있고, CI에서 인프라를 바꾸는 것은 실익 대비 위험이 크다. **검사·리뷰는 자동,
반영은 수동**인 구조다. 배관(`plan`/`apply` job, http backend 선언)은 만들어 뒀고
활성화 절차는 §4-5에 남겼다.

## 4-2. 현업 구성과의 차이

규제 산업(금융/공공/통신)의 내부망 형상관리 구성과의 대응 관계:

| 구성 요소 | 현업 (내부망 표준) | 이 프로젝트 | 차이의 이유 |
|---|---|---|---|
| Git 서버 | GitLab Self-Managed를 내부망 서버에 HA 구성, 백업, LDAP/SSO | GitLab CE 컨테이너 1개, 로컬 계정 | HA·백업·인증 연동은 "서버 운영" 영역 — 형상관리 **구조** 확인에는 불필요 |
| CI 러너 | 전용 러너 서버 팜, 태그로 워크로드 분리 | 러너 컨테이너 1개 (docker executor) | 1개로도 "push 트리거 → 격리 컨테이너에서 검사" 원리는 동일 |
| Terraform state | S3 호환 스토리지 + lock, 또는 GitLab managed state | GitLab CE 내장 managed state | 현업 선택지 중 하나를 그대로 사용 — 사실상 차이 없음 |
| Secrets | Vault 중앙 관리, 동적 발급 | GitLab CI/CD Variables (masked) | "코드에 평문 금지 + 주입" 원칙은 동일 |
| apply 게이트 | 승인자 지정 + `when: manual`, 환경별 단계 승격 | 수동 apply, 환경 1개 | 환경이 1개라 승격 단계가 성립하지 않음 |
| Provider 미러 | Nexus/Artifactory 사설 미러 (폐쇄망) | 공개 레지스트리 직접 사용 | 실제 폐쇄망이 아님 — 미러 구축은 비용 과대 |

**구조는 보존하고 규모만 축소한 것**이다. 사설 Git 서버, 사설 러너, push 트리거 자동 검사,
원격 state + lock, secrets 주입, 머지 기반 배포라는 골격은 전부 동일하다.

## 4-3. 기동과 러너 등록

GitLab CE + 러너는 `docker-compose`로 띄운다. 포트는 8929(HTTP)/2222(SSH) — 로컬 22번 충돌 회피.

**주소 설계가 가장 헷갈리는 부분이다.** 세 주체가 같은 GitLab을 서로 다른 경로로 본다:

| 주체 | 쓰는 주소 | 이유 |
|---|---|---|
| 노트북 브라우저·`git push` | `http://localhost:8929` | 호스트에서 보는 포트 매핑 |
| 러너 컨테이너 | `http://gitlab:8929` | 같은 Docker 네트워크의 컨테이너 이름 |
| job 컨테이너 (clone) | `http://gitlab:8929` | 러너 설정의 `clone_url`로 강제 |

`external_url`을 `gitlab.local`로 두고 `/etc/hosts`에 등록하는 방법도 있지만 sudo가 필요하다.
sudo 없이 가려면 `external_url`은 `localhost`로 두고 **러너에만 `clone_url`을 주는** 쪽이 간단하다.

```bash
docker-compose up -d
docker logs -f gitlab                                  # 초기화 3~5분

# 컨테이너가 healthy여도 nginx는 아직 안 떠 있을 수 있다 — 실제 HTTP 200을 기준으로 삼는다
until [ "$(curl -s -o /dev/null -w '%{http_code}' http://localhost:8929/users/sign_in)" = "200" ]; do sleep 10; done

docker exec gitlab cat /etc/gitlab/initial_root_password | grep Password:
  # 이 파일은 24시간 뒤 자동 삭제 — 로그인 후 즉시 변경
```

러너 등록은 UI에서 토큰을 복사해도 되지만, **전 과정을 API로 처리하면 재현 가능**하다
(폐쇄망 자동화의 실제 방식이기도 하다). 개인 액세스 토큰(PAT)을 만들어 프로젝트 생성 →
러너 토큰 발급 → 러너 등록까지 CLI로 끝낼 수 있다.

```bash
PAT="<GITLAB_PAT>"    # 로컬 전용 자동화 토큰

# ① root PAT 생성
docker exec gitlab gitlab-rails runner "
  u = User.find_by_username('root')
  t = u.personal_access_tokens.create!(scopes: ['api','write_repository'],
                                       name: 'automation', expires_at: 30.days.from_now)
  t.set_token('${PAT}'); t.save!; puts 'PAT_OK'"

# ② 프로젝트 생성
curl -s -X POST "http://localhost:8929/api/v4/projects" -H "PRIVATE-TOKEN: ${PAT}" \
  -d "name=openstack-iac" -d "visibility=private" -d "initialize_with_readme=false"

# ③ 러너 토큰 발급
RUNNER_TOKEN=$(curl -s -X POST "http://localhost:8929/api/v4/user/runners" \
  -H "PRIVATE-TOKEN: ${PAT}" \
  -d "runner_type=project_type" -d "project_id=1" \
  -d "description=docker-runner" -d "run_untagged=true" \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

# ④ 러너 등록 — executor는 docker (job마다 격리 컨테이너)
docker exec gitlab-runner gitlab-runner register --non-interactive \
  --url "http://gitlab:8929" --token "${RUNNER_TOKEN}" \
  --executor "docker" --docker-image "alpine:latest" --docker-network-mode "gitlab-net"

# ⑤ job 컨테이너의 clone 주소 교정 — 없으면 job이 localhost:8929로 clone을 시도해 실패
docker exec gitlab-runner sed -i 's|^\(\s*\)url = .*|\1url = "http://gitlab:8929"\n\1clone_url = "http://gitlab:8929"|' \
  /etc/gitlab-runner/config.toml
docker restart gitlab-runner
```

`--docker-network-mode`와 `clone_url` 중 **하나라도 빠지면 clone 단계에서 실패**한다. 전자는
job 컨테이너를 같은 네트워크에 붙이고, 후자는 그 네트워크에서 통하는 주소를 알려준다.

> remote URL에 PAT를 넣어 push하면 `git remote -v`에 토큰이 노출된다. 로컬 실습이라
> 그렇게 했지만, 실제 환경에서는 credential helper나 SSH 키를 쓴다.

## 4-4. 검사 파이프라인 — 이 단계의 핵심

push/MR마다 자동 실행되는 IaC 검사 4종. 전문은 [`.gitlab-ci.yml`](../.gitlab-ci.yml).

| job | 잡는 것 |
|---|---|
| `fmt` | `terraform fmt -check -recursive -diff` — 포맷 위반 |
| `tflint` | `tflint --recursive` — 미사용 변수, 타입 누락, deprecated 문법 |
| `validate` | `terraform init -backend=false && terraform validate` — 문법/참조 오류 |
| `security_scan` | `tfsec . --soft-fail` — SG 전면 개방, 평문 secret 등 |

> **`entrypoint: [""]`를 빠뜨리지 말 것.** `terraform`/`tflint`/`tfsec` 이미지는 도구 자체를
> ENTRYPOINT로 갖는다. 러너는 job 스크립트를 셸에 넘겨 실행하므로, 해제하지 않으면
> `terraform sh ...`로 실행돼 `Terraform has no command named "sh"`로 죽는다.
> 첫 파이프라인이 정확히 이걸로 실패했다 ([troubleshooting #9](troubleshooting.md)).

### 첫 실행에서 자동 검사가 잡아낸 것

원래는 fmt 위반을 **고의로** 넣어 "검사가 막아주는지" 확인할 계획이었다. 필요 없었다 —
**첫 파이프라인이 진짜 결함 2건으로 실패**했다.

1. `hashicorp/terraform` 이미지의 ENTRYPOINT 미해제 → job이 `terraform sh`로 실행돼 실패
   ([#9](troubleshooting.md))
2. 변수 9개에 `type` 선언 누락 → `terraform validate`는 통과하지만 `tflint`가 검출
   ([#10](troubleshooting.md))

2번이 특히 뼈아프다. **사람이 3일간 못 본 결함을 파이프라인 첫 실행이 9건 즉시 잡았다.**
`validate` 통과는 코드가 좋다는 뜻이 아니다 — 문법 검사와 품질 검사는 잡는 결함의 종류가
다르므로 파이프라인에 둘 다 있어야 한다.

수정 후 #2 파이프라인에서 4개 job 전부 통과. tfsec은
`blocks processed 56 / passed 15 / critical·high·medium·low 0`.

## 4-5. 자동 apply — 배관만 깔고 실행하지 않음

`ENABLE_APPLY == "true"` + `when: manual` 이중 잠금으로 배관은 만들었지만 켜지 않았다. 이유:

1. **state가 다른 곳에 있다.** 진짜 `terraform.tfstate`는 DevStack 호스트의 로컬 파일이다.
   그 상태로 CI에서 apply하면 CI 쪽 state가 비어 있으니 **이미 존재하는 리소스를 새로 만들려
   시도**한다. 이름 충돌로 실패하거나, 최악의 경우 실환경을 훼손한다.
2. **자격증명이 CI에 없다.** DevStack의 `OS_PASSWORD`는 사람만 안다.
3. **인증 방식이 다르다.** `providers.tf`는 `cloud = "devstack-admin"`으로 `clouds.yaml`
   **파일**을 읽는다. CI에 환경변수만 넣어서는 인증되지 않는다.

참고로 노트북에서 DevStack API로의 네트워크 도달성은 확인했다(HTTP 300). 막힌 것은
네트워크가 아니라 state와 자격증명이다.

켠다면 순서는 이렇다:

1. **`clouds.yaml`을 File 타입 CI 변수로 등록** — Key `OS_CLIENT_CONFIG_FILE`,
   **Type을 반드시 `File`로**. GitLab이 job 컨테이너의 임시 파일로 만들어 주고, gophercloud가
   이 변수를 읽으므로 `providers.tf`는 고칠 필요가 없다.
2. **state 이관** — DevStack 호스트에서 `terraform init -migrate-state`로 GitLab managed
   state(http backend)로 옮긴다. **이관 전 `terraform.tfstate`를 반드시 백업**한다. state를
   잃으면 Terraform이 실환경을 관리하지 못하게 되고, 복구는 리소스마다 `import`를 일일이
   해야 한다.
3. **`plan`을 먼저 수동 실행** — `No changes. Your infrastructure matches the configuration.`이
   나와야 정상이다. **변경이 잔뜩 뜨면 state 이관이 실패한 것이므로 apply를 눌러선 안 된다.**
4. plan이 깨끗하면 `apply` 실행.

현업에서도 apply에 `when: manual` 승인 게이트를 거는 경우가 많다.

## 자주 만나는 문제

| 증상 | 원인/대응 |
|---|---|
| GitLab 기동 후 502 / 빈 응답 | 초기화 미완료 — `healthy`여도 nginx는 아직일 수 있다. HTTP 200 폴링으로 판단 |
| `docker: unknown command: docker compose` | compose 플러그인 미설치 — standalone `docker-compose` 사용 (**실제 발생**) |
| `Terraform has no command named "sh"` | 이미지 ENTRYPOINT 미해제 — `entrypoint: [""]` (**실제 발생**, [#9](troubleshooting.md)) |
| tflint가 exit code 2 | 경고 검출 = 실패가 정상 동작. 코드를 고치는 게 정답 (**실제 발생**, [#10](troubleshooting.md)) |
| 러너가 job을 안 가져감 | 러너 등록 주소가 `localhost` — `http://gitlab:8929`로 재등록 |
| job 컨테이너에서 clone 실패 | `--docker-network-mode gitlab-net` + `clone_url` 둘 다 필요 |
